Chaque partie dit ce qui a été fait, pourquoi, et ce qu'il faut en retenir pour ses propres projets.

1. Le but et les deux produits

Le but est pédagogique : former un apprenant à l'aéronautique, du niveau zéro jusqu'au brevet de pilote et au-delà. Toutes les décisions du projet sont jugées sur ce but. Une fonction jolie mais qui n'apprend rien passe après une fonction simple qui fait comprendre un vrai principe du vol.

ProduitFormeRôle
PLANE TRAJECTORIES (gratuit)un seul fichier HTML d'environ 3 Mo, sans serveurla vitrine : s'ouvre partout, même hors ligne, sur téléphone
PLANE SIMULATOR (Pro)site React + API Symfony + base MySQLle produit : comptes, cours complets, PDF, trafic réel, évolutions

La version gratuite a été construite d'abord. La version Pro a été lancée ensuite (le « GO PRO »), en reprenant tout le travail existant au lieu de repartir de zéro.

À retenirCommencez par une version simple qui marche et qu'on peut montrer. On la transforme ensuite en produit, sans jeter ce qui fonctionne.

2. La méthode de travail

  • Un journal des demandes. Chaque demande est notée avec sa date et son texte exact dans MAJ-2.md (tout : fait et à faire). Le fichier MAJ2-BIS.md ne garde que ce qui reste à faire. Une demande terminée y est retirée et marquée « FAITE » dans MAJ-2, avec le numéro du commit.
  • Des raccourcis pour aller vite : « -> » (à traiter après le travail en cours), « vs » (version autonome à tester), « jp » (jauge d'avancement), « c » (continuer), « jlf » (finir sans s'arrêter).
  • Des branches Git. Le travail non testé va sur une branche à part (f21-meteo, f37-radio-v2…). Il n'arrive sur main qu'une fois tous les tests au vert.
  • Pas de régression. Chaque ajout est vérifié sur les 8 appareils, sur ordinateur et sur téléphone, en version servie et en version autonome.
  • Des décisions réservées à l'auteur : le nom de domaine, les fréquences radio, les procédures d'approche, les caractéristiques de l'A350, les sources de trafic et leurs licences. L'outil peut proposer, mais ne décide jamais à la place du propriétaire du projet.
À retenirUn projet qui avance vite a besoin d'une trace écrite : demandes, décisions, état. C'est ce qui permet de reprendre le travail le lendemain, ou de le confier à quelqu'un d'autre.

3. L'architecture : qui fait quoi

 Navigateur de l'élève                         Serveur (o2switch)
 ┌───────────────────────────────┐            ┌──────────────────────────────┐
 │ Interface React + TypeScript  │  JSON      │ API Symfony 7.4 (PHP 8.2+)   │
 │  • pages : Parcours, Cours…   │ ─────────▶ │  • comptes, connexion        │
 │  • Three.js : la 3D           │ ◀───────── │  • données /api/data/…       │

 └───────────────────────────────┘ de session │  • base MySQL (Doctrine)     │

  • Le frontend (frontend/) est en React 19 et TypeScript. Il est compilé par esbuild, un outil très rapide qui transforme le TypeScript et le JSX en un seul fichier app.js. Le routage passe par l'ancre de l'URL (#/cours/…), ce qui évite toute configuration serveur.
  • Le backend (backend/) est une API Symfony : il ne renvoie pas de pages, seulement du JSON (ou un PDF). Il garde les comptes, contrôle les accès et sert les données.
  • Les données (data/*.json) : appareils, aéroports, missions, cours. Elles ont été extraites automatiquement du moteur d'origine, sans rien recopier à la main.
  • Le moteur d'origine (legacy/) : le simulateur de la version gratuite, utilisé tel quel pendant que ses morceaux sont réécrits un par un (voir la partie 6).

Pourquoi séparer le frontend et l'API ? Chaque partie a un seul métier. L'API pourra servir plus tard une application mobile, et l'interface pourra changer sans toucher à la sécurité. Le serveur, lui, est le seul juge de qui a le droit de voir quoi.

4. La 3D expliquée depuis zéro

La 3D dans un navigateur passe par WebGL, une interface de très bas niveau qui dessine des triangles avec la carte graphique. Personne n'écrit du WebGL à la main pour un projet comme celui-ci. On utilise Three.js, une bibliothèque qui donne des objets simples à manipuler. Il suffit de cinq notions :

NotionCe que c'estÉquivalent « web »
Scènele monde : tout ce qui existele DOM
Caméral'œil : sa position, sa direction, son angle de vuela fenêtre du navigateur
Maillage (mesh)un objet : une géométrie (la forme, faite de triangles) + un matériau (la couleur, la brillance)un élément HTML + son CSS
Lumièresoleil, lumière ambiante : sans elle, tout est noir—
Rendule dessin de la scène vue par la caméra, environ 60 fois par secondele rafraîchissement de l'écran

Le plus petit programme Three.js possible : un cube qui tourne.

import * as THREE from 'three';
const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(60, innerWidth / innerHeight, 0.1, 1000);
camera.position.z = 3;                                  // l'œil recule de 3 unités
const renderer = new THREE.WebGLRenderer({ antialias: true });
renderer.setSize(innerWidth, innerHeight);
document.body.appendChild(renderer.domElement);         // un <canvas> dans la page
const cube = new THREE.Mesh(new THREE.BoxGeometry(1, 1, 1), new THREE.MeshStandardMaterial({ color: 0x3ad0ff }));
scene.add(cube, new THREE.AmbientLight(0xffffff, 0.4));
const sun = new THREE.DirectionalLight(0xffffff, 1); sun.position.set(2, 3, 4); scene.add(sun);
function boucle() {                                     // la « boucle de rendu »
  requestAnimationFrame(boucle);                        // le navigateur rappelle boucle() à chaque image
  cube.rotation.y += 0.01;                              // on modifie le monde…
  renderer.render(scene, camera);                       // …puis on le redessine
}
boucle();

Tout le simulateur repose sur ce schéma : à chaque image, on calcule la nouvelle position de l'avion (la physique), on déplace les objets et la caméra, puis on redessine.

Les techniques utilisées dans le projet

  • Des avions faits de formes simples. Pas de gros fichiers 3D téléchargés : chaque appareil est assemblé avec des cylindres, des sphères et des formes extrudées. Le fichier reste léger et s'ouvre sur un téléphone.
  • L'origine flottante. La Terre est immense : à des millions de mètres de l'origine, les nombres à virgule de la carte graphique perdent en précision et l'image tremble. Le monde est donc recentré en permanence sur l'avion, qui reste près du point (0, 0, 0).
  • Des textures dessinées dans un <canvas> : marquages de piste, écrans du poste de pilotage. On dessine en 2D, puis on « colle » le dessin sur un objet 3D.
  • Le brouillard de la scène (scene.fog) : au-delà d'une distance, les objets se fondent dans une couleur. C'est ce qui donne la profondeur, et c'est ce que la météo « Brouillard » réduit à 200 m.
  • Les sprites : des images toujours tournées vers la caméra (feux de piste, halos). Elles coûtent très peu cher à dessiner.
  • Le poste de pilotage interactif : on lance un « rayon » depuis le doigt ou la souris (Raycaster) pour savoir quel instrument a été touché, puis on l'ouvre en grand.
À retenirLa 3D, c'est une scène, une caméra, des objets et une boucle qui redessine. Commencez par le cube qui tourne, puis ajoutez une chose à la fois. Sur téléphone, comptez les triangles et les textures : la performance fait partie du design.

5. La physique du vol

À chaque pas de temps (une fraction de seconde), le moteur applique les lois de Newton à l'avion :

  • quatre forces : portance (les ailes), poids (la masse), poussée (les moteurs), traînée (la résistance de l'air) ;
  • l'atmosphère type (ISA) : la densité de l'air baisse avec l'altitude, et donc la portance et la poussée aussi ;
  • le vent : il s'ajoute à la vitesse de l'avion et décide de la vitesse sol et de la dérive ;
  • les commandes : manche, palonnier, manettes, volets, train, freins, et le pilote automatique.

Ce moteur a été réécrit en TypeScript (frontend/src/engine/flight.ts). Pour prouver que la réécriture ne change rien, 12 vols complets sont rejoués pas à pas dans l'ancien et dans le nouveau moteur. Les résultats doivent être identiques, avec un écart nul (tests/parity_flight.py). C'est un test de parité.

À retenirQuand on réécrit un morceau critique, on garde l'ancien et on compare les deux sur les mêmes entrées. Si les sorties sont identiques, on peut remplacer sans crainte.

6. Faire vivre l'ancien moteur dans le nouveau site

Réécrire d'un coup un simulateur de près de 3 Mo de code serait risqué et long, et il ne marcherait pas pendant des mois. Le choix a été de garder l'ancien moteur en marche et de le remplacer module par module (la « migration progressive », parfois appelée strangler fig).

  • L'onglet « Simulateur » charge le moteur d'origine dans une iframe (une page dans la page), avec srcdoc. En ligne, le code du moteur est servi par l'API, et seulement aux comptes connectés.
  • React lui envoie des ordres simples par l'adresse, par exemple #/simulateur/go:a320:full-fw pour lancer tel parcours avec tel appareil.
  • Chaque module réécrit en TypeScript est vérifié par un test de parité avant de remplacer l'original.

7. Météo et radio : étendre sans casser

Les boutons radio (Répéter, Standby, Radio ▾, Mayday / Pan-Pan) et le choix de la météo n'ont pas été codés dans le moteur d'origine. Ce sont des extensions (frontend/src/legacy-ext/radio.ts et meteo.ts) injectées dans l'iframe une fois le moteur prêt. Elles « enveloppent » ses fonctions :

const freinageOrigine = window.brkEff;            // on garde la fonction du moteur…
window.brkEff = function () {                     // …et on la remplace par une version qui l'appelle
  const e = freinageOrigine();
  return S.onGround ? e * etatDePiste().k : e;    // piste mouillée : ×0,65 ; neige : ×0,45 ; glace : ×0,25 [ESTIMÉ]
};

C'est le principe du décorateur : on ajoute un comportement sans réécrire l'original, et on peut le retirer à tout moment. La météo choisie produit de vrais messages METAR, marqués [SIMULÉ]. Tout ce que le moteur tirait déjà du METAR suit tout seul : ATIS, vent, rafales, givrage et sons. L'extension ajoute ce qui manquait : l'état de la piste et le freinage, la visibilité, la pluie et la neige à l'écran, la turbulence d'orage, la foudre et la voix de synthèse du pilote.

Même méthode pour les extensions suivantes : tourAvion.ts (arrêts devant chaque point de la visite, flèches rouges, bilan rangé dans les documents, zones de danger des moteurs en marche) et equipage.ts (tablette de documents, toutes les annonces et check-lists de l'équipage en « question / réponse », annonces en direct comme « V1 » ou « minimums » d'après la vitesse et la hauteur réelles). Le choix de la météo agit aussi sur la densité de l'air : ρ = P / (R·T), avec la pression tirée du QNH et la température du METAR. Par temps chaud, l'air est moins dense : la portance et la poussée baissent, le décollage s'allonge. C'est de la physique, pas un effet visuel.

8. Les données : ne jamais rien inventer

Un outil de formation qui affiche une fausse fréquence ou une fausse masse maximale peut induire un élève en erreur. Chaque donnée porte donc un statut :

StatutSensExemple
[OFFICIEL] / [RÉFÉRENCÉ]publié par une source identifiéepoussée de l'A350 (certificat EASA), fréquences (AirNav, SIA)
[OBSERVÉ]mesuré dans la réalitéMETAR réels, trafic reçu par l'antenne
[CALCULÉ]obtenu par un calcul à partir de données sourcéesdistance de décollage du banc d'essai
[ESTIMÉ]ordre de grandeur raisonnable, sans source exactecoefficients de freinage sur piste mouillée
[SIMULÉ]fabriqué pour l'exercicemétéo choisie, indicatif « SIMU 350 », cellules orageuses

Quelques règles sont fixes : aucune voix réelle d'équipage n'est fabriquée, aucune image d'accident ou de victime n'est utilisée, et les marques des compagnies sont fictives (Aéralis, Vectra…).

9. Comptes, sécurité et espace Admin

  • Mots de passe : jamais stockés en clair. Symfony les hache avec l'algorithme « auto » (aujourd'hui bcrypt ou argon2).
  • Session : un cookie HttpOnly posé par le serveur. Le JavaScript de la page ne peut pas le lire, ce qui limite les vols de session.
  • Limitation des tentatives : 5 essais de connexion par adresse et par IP en 15 minutes.
  • Mot de passe oublié : un lien à usage unique, valable 1 h (SymfonyCasts ResetPasswordBundle). La réponse est la même que l'adresse existe ou non, pour ne pas révéler qui est inscrit.
  • Contrôle d'accès côté serveur (security.yaml, access_control) : sans compte, l'API refuse les données, le moteur et les PDF. Masquer un bouton dans React ne protège rien, car n'importe qui peut appeler l'API directement.
  • Espace Admin : rôle ROLE_ADMIN. La route /api/admin/… répond 401 sans compte, 403 pour un élève et 200 pour un administrateur. Le premier administrateur est créé en ligne de commande, et le mot de passe est tapé au clavier, masqué :
php bin/console app:admin:create vous@cockpitschool.com
À retenirLa sécurité se décide sur le serveur. Le navigateur appartient à l'utilisateur, et tout ce qui s'y trouve peut être lu ou modifié.

10. Les cours, les exercices et les PDF

  • Trois cycles : Cours 0 (sciences utiles : 7 thèmes, 210 exercices), Cours I · Initiation (76 modules), Cours II · Confirmé (niveau ATPL : 14 modules, 280 exercices).
  • Les exercices sont écrits en Python (tools/cours/). La bonne réponse est calculée par le programme, pas tapée à la main. Un contrôle (assert) refuse un exercice dont deux options seraient identiques. python3 tools/cours/build.py produit les fichiers JSON lus par le site.
  • Les PDF : générés par le serveur (dompdf), ou à défaut par l'impression du navigateur (#/imprimer/…).
À retenirQuand un contenu contient des calculs, générez-le par un programme qui fait les calculs : une erreur de frappe dans un corrigé fait perdre la confiance d'un élève.

11. Les tests : prouver que ça marche

Pour tester l'interface sans serveur Symfony, un serveur simulé (tests/serveur_simule.py) répond comme les vrais contrôleurs. Il ne remplace pas les tests PHPUnit. Une règle est fixe : on ne remplace jamais une vraie dépendance par un faux pour déclarer un test réussi. Les tests PHPUnit sont écrits, mais ils n'ont pas encore été exécutés : les bibliothèques PHP (Packagist) étaient inaccessibles dans l'environnement de développement. Ils seront lancés lors de l'installation chez o2switch.

12. La version autonome (un seul fichier)

tools/standalone.py fabrique un seul fichier HTML d'environ 4,5 Mo. Il contient le CSS, le JavaScript, Three.js, toutes les données et le moteur d'origine. Ce fichier s'ouvre sur un téléphone sans connexion : c'est le moyen le plus rapide de faire relire une version. Il est en « démonstration hors ligne » (tout est ouvert, avec un bandeau) et ne doit jamais être publié sur le site.

13. Le trafic aérien réel et le Raspberry Pi

Les avions envoient en permanence leur position par radio (ADS-B, 1 090 MHz). Un Raspberry Pi (un petit ordinateur à bas prix), une clé radio et une antenne suffisent à les recevoir. Le script tools/recepteur/ envoie ces positions à l'API, avec un jeton secret, au format compressé gzip. L'API peut aussi interroger OpenSky Network et Flightradar24. Aucune source n'est active par défaut : il faut choisir les sources, vérifier leurs conditions d'utilisation et souscrire les abonnements nécessaires. Ce choix reste à l'auteur.

14. Travailler avec une IA

  • L'IA écrit du code, rédige et teste. L'auteur fixe le but, valide et décide.
  • Les demandes sont précises et notées. Chaque livraison est vérifiée par des tests et par une version autonome que l'auteur ouvre lui-même.
  • Les commits portent le nom de l'auteur. La responsabilité du produit reste humaine.
  • Une IA peut se tromper. Dans ce projet, les tests ont révélé de vraies erreurs : un indicatif répété deux fois, la mauvaise tour de contrôle interrogée (deux tours de Kennedy portent le même nom), un réglage de brouillard qui cassait l'affichage. Toutes ont été corrigées parce que les tests existaient.
À retenirUne IA est un excellent accélérateur, à condition de garder la méthode : un but clair, un journal, des tests, des validations humaines.

15. Le volet entrepreneurial

  • Le modèle : une version gratuite qui attire (PLANE TRAJECTORIES) et une version Pro avec comptes, qui pourra être payante.
  • Le nom de domaine : cockpitschool.com, choisi par l'auteur le 20/11/2026 (planesimulator.com et flapsone.com étaient déjà pris). L'achat se fait chez un bureau d'enregistrement (o2switch ou un autre).
  • L'hébergement : o2switch, un hébergeur mutualisé français qui accepte PHP, MySQL et Composer. Vérifiez sur leur site les versions de PHP proposées et le prix en vigueur.
  • Les coûts à prévoir : domaine, hébergement, matériel du récepteur (Raspberry Pi), abonnements éventuels aux données de trafic, licences des images.
  • Le droit : images (les illustrations générées et les photos de référence n'ont pas toutes la même licence), données de trafic (conditions de chaque fournisseur), marques (pas de logos de constructeurs ni de compagnies réelles), données personnelles des élèves (RGPD : mentions légales, politique de confidentialité, droit à l'effacement à mettre en place avant l'ouverture).
  • Avant la mise en ligne : installer Symfony chez o2switch, lancer PHPUnit, créer l'administrateur, configurer l'envoi d'e-mails (lien de réinitialisation), mettre en place des sauvegardes de la base, publier les mentions légales.
À retenirUn produit numérique ne se résume pas au code : domaine, hébergement, droit, sauvegardes et support font partie du travail, et ont un coût à prévoir dès le départ.
